# Design anti-slop for RandoMeal

Снимать статистически типовые AI-паттерны, не подменяя ими продуктовую стратегию или личный вкус.
Считать каталог системой кандидатов для проверки, а не генератором бренда.

## Приоритет источников

Разрешать противоречия в таком порядке:

1. требования продукта, safety, accessibility и подписанный discovery decision;
2. `docs/product/quality-and-design.md`, актуальные Figma variables и токены в коде;
3. подтверждённые пользователем бренд-решения;
4. [`references/catalog.md`](references/catalog.md);
5. нейтральные эвристики агента.

Не отменять осознанное решение только потому, что оно совпало с T-правилом. Зафиксировать
исключение и больше его не флажить в рамках задачи.

## Режимы

- `audit` — режим по умолчанию. Найти нарушения, показать точные места, severity, объяснение и
  минимальный системный фикс. Ничего не менять без согласования.
- `fix` — исправить согласованный объём и дать отчёт до/после. Начинать сразу только если
  пользователь явно попросил исправлять без отдельного согласования.
- `creation review` — при создании нового UI провести короткий self-audit до показа результата;
  это не требует отдельной паузы, но найденные нарушения исправить до handoff.

## Обязательный workflow

1. Прочитать релевантные требования и определить задачу экрана. Для recommendation UI проверить
   `docs/product/discovery-decisions.md`: skill не выбирает `single`, `shortlist` или `hybrid` вместо
   Decision Gate D0.
2. Найти источник дизайн-системы: Figma variables/components, `DESIGN.md`, theme/tokens и
   существующие компоненты. Не создавать новые raw hex, spacing или радиусы при наличии токенов.
3. Определить носитель и применимые проверки:
   - Figma/mobile — визуальная и структурная проверка, accessibility, компоненты и токены;
   - React Native/Expo — style objects, theme tokens, component variants и render screenshots;
   - web/admin — визуальная проверка плюс grep/DOM/CSS-эвристики каталога;
   - screenshot — только аудит; не утверждать точные причины без кода/узлов.
4. Пройти каталог в порядке `ban -> system -> flags -> copy`. Применять только правила,
   релевантные носителю и жанру экрана.
5. Выдать audit в формате ниже. Для `fix` дождаться подтверждения, если пользователь не разрешил
   исправлять сразу.
6. Делать минимальные правки через существующие токены и компоненты. Не добавлять «характер»
   случайным цветом, шрифтом, анимацией или декоративным паттерном.
7. Проверить результат на поддерживаемых размерах, large text, contrast, reduced motion,
   loading/empty/error/offline и platform differences, где они применимы.
8. Для Figma повторно получить screenshot изменённых фреймов. Для кода запустить релевантные
   component tests/typecheck и визуальный smoke test.

## Интерпретация каталога в мобильном продукте

- `ban` означает «исправить или документировать осознанное исключение», а не абсолютный запрет.
- T17 и T27 относятся к web/landing/admin shell и не переносятся механически на mobile navigation.
- Hover-правила T12/T19 применяются к web; на mobile проверять press/focus/motion equivalents.
- T24 не запрещает настоящие inline-ссылки; на mobile action должен иметь корректную роль и
  достаточный touch target.
- Числовые пороги каталога — smoke thresholds. Не использовать их как доказательство качества без
  просмотра композиции.
- Статистические веса и внешние ссылки в каталоге информационные; они не являются продуктовым
  research RandoMeal.

## Figma и реализация

- Перед созданием компонентов искать существующие library assets, variables и styles.
- Для новых компонентов задавать Auto Layout, variants/states, semantic variable bindings,
  accessibility annotation и поведение текста.
- Создавать один component source для Figma и кода, где возможно; использовать Code Connect после
  стабилизации API компонента.
- Не ограничиваться красивым default state. Проверять все состояния, перечисленные в
  `docs/product/quality-and-design.md`.
- Не копировать чужой экран целиком. Референс использовать для UX-паттерна, а не визуального клона.

## Формат аудита

```text
DESIGN ANTI-SLOP AUDIT · <объект> · <носитель>
Контекст: <источник токенов/бренд-решений и задача экрана>
Баны:    <T# · точное место · почему · системный фикс>
Система: <T# · точное место · почему · системный фикс>
Флаги:   <T# · точное место · вопрос/предложение>
Копирайт:<T21 или «чисто»>
Чисто по:<проверенные группы без находок>
Характер:<одно-два предложения, где продукт может стать узнаваемее>
Исключения:<подтверждённые осознанные решения>
```

Завершать честно: типовые паттерны сняты или перечислены; окончательный вкус и смелые решения
требуют продуктового/дизайнерского решения. Не использовать эту фразу как отказ от конкретного
результата.
